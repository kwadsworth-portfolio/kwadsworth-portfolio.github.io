AWS Cloud Security Case Study

Designing and implementing a secure AWS environment with a focus on identity, network segmentation, logging and risk-based control selection.

← Back to Projects View project evidence →

1. Overview

Project context and goals.

Lab projectAWS

Project Overview

This lab-style project was designed to mirror how a small organisation might establish a secure AWS footprint. The goal was to apply cloud security principles in a structured way, linking each design choice back to risk, governance and operational requirements.

2. Scope & Assumptions

What was in scope and the constraints applied.

Scope

Environment

  • Single AWS account representing a small organisation or business unit.
  • Mix of internet-facing and internal workloads.
  • Focus on core security controls rather than advanced cloud-native services.
  • Emphasis on auditability, traceability and least-privilege access.

3. Architecture & Design

Key design decisions and their security rationale.

ImplementedNetwork

VPC & Subnet Design

  • VPC with separate public and private subnets.
  • Internet-facing resources in public subnets only where required.
  • Application and data components in private subnets.
  • Security groups limiting traffic based on resource role.
ImplementedIAM

Identity & Access

  • IAM roles for services instead of long-lived access keys.
  • Roles defined for admins, developers and read-only users.
  • Least-privilege policies mapped to specific job functions.
  • Access design documented and linked to governance expectations.

4. Logging, Monitoring & Evidence

Audit trail and visibility controls.

ImplementedCloudTrail

Audit Logging

  • CloudTrail enabled for account-level activity logging.
  • Logs centralised and retained for ongoing review.
  • Console logins and IAM changes verified as captured.
  • Screenshots and configs captured as project evidence.

Goal: demonstrate "who did what, where and when" in line with audit and incident response requirements.

5. Risk-Based Decisions & Next Steps

Trade-offs noted and future enhancements identified.

Decisions

Trade-offs & Residual Risk

  • Services deferred to a later phase (WAF, GuardDuty).
  • Default configurations assessed — hardening applied where needed.
  • Residual risks documented for each deferred control.
Future

Planned Enhancements

  • Integration with a SIEM for centralised detection.
  • Automated compliance checks using AWS Config.
  • Detailed threat modelling for critical workloads.
  • WAF and GuardDuty deployment in follow-on phase.
Outcome: A documented, evidence-backed AWS security build demonstrating identity, network, logging and governance controls — structured for review by hiring managers and technical interviewers.
