SIEM Visibility & Detection Case Study

Establishing security visibility through log collection, detections and a lightweight incident response workflow — linking alerts back to business risk and operational impact.

← Back to Projects View project evidence →

1. Overview

This project focuses on building practical experience with a Security Information and Event Management (SIEM) platform. The goal is to move from raw log data to meaningful alerts and investigations, using a structured, risk-aware approach that mirrors how SOC and security teams operate in practice.

2. Scope & Assumptions

  • Small set of systems — one Windows host and one Linux host running as lab virtual machines.
  • Focus on authentication events, system activity and core security log sources.
  • Objective is understanding the full flow: log → event → alert → investigation.
  • Assumes a hosted or lab SIEM platform (Splunk) is available for testing and configuration.

3. Log Sources & Onboarding

I began by selecting which log sources would add the most value for a small environment, then onboarded them into the SIEM:

  • Authentication logs — logon success and failure events, account lockouts.
  • System logs covering key services and security-relevant activity.
  • Sysmon telemetry for process creation, command-line and network events.

The aim was to ensure that any investigation into suspicious activity would have sufficient supporting detail to be meaningful and traceable.

4. Detections & Use Cases

I defined a set of practical detection use cases that reflect common attack patterns:

  • Multiple failed logins followed by a successful login from the same source (brute force).
  • Authentication events occurring outside expected working hours.
  • New local user creation on a server or critical host.
  • Suspicious PowerShell execution using encoded commands.

For each use case, I created detection rules or SPL queries in Splunk and validated that they would trigger correctly under the expected conditions.

5. Dashboards, Triage & Investigation

To support ongoing monitoring and incident handling, I:

  • Built dashboards to surface failed logins, account lockouts and key security events.
  • Configured alert views to support rapid triage and prioritisation.
  • Performed test investigations using simulated suspicious activity.
  • Documented the steps from initial alert through to basic root cause analysis.

This process helped connect the technical view — logs and alerts — with the operational view of what an event means for the organisation.

6. Incident Workflow & Lessons Learned

I outlined a lightweight incident handling workflow covering:

  • Alert review and initial triage against defined severity thresholds.
  • Enrichment and gathering of additional context to support decisions.
  • Escalation criteria and potential containment steps.
  • Documentation of findings and recommendations for improvement.

I also captured lessons learned around noise reduction, alert tuning and the importance of understanding normal system behaviour before defining what constitutes a suspicious event.

7. Next Steps

Future enhancements to this lab could include:

  • Integrating additional log sources such as cloud platforms or SaaS applications.
  • Building more advanced correlation rules across multiple systems and event types.
  • Linking detections to a formal playbook or SOAR-style automation workflow.
  • Mapping detections to MITRE ATT&CK for structured coverage analysis.

Overall, this project demonstrates how I approach visibility, detection and incident handling using a structured and risk-based perspective, rather than focusing purely on tooling.
